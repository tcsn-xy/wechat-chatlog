# 原理：macOS 上把微信 4.x 聊天记录完整取出来

这份文档记录整套方法的**为什么**。想直接用工具，看根目录的 `README.md` 就够。

---

## 0. 总览：四道关卡

微信 4.x 在 macOS 上把聊天记录保护得相当好。要拿到里面的数据，得依次破四道关：

```
① 沙盒 / TCC        外部进程（含 root）完全读不了微信容器
        ↓  借微信自己的权限
② 硬编码签名        Hardened Runtime 拒绝任何调试器附加
        ↓  复制一份 App，只给副本重签名
③ SQLCipher         所有数据库都是加密的，密钥在内存里
        ↓  lldb 断点，让微信自己把密钥交出来
④ 自定义媒体加密   图片 .dat 不是标准格式，还有 wxgf/HEVC 变体
        ↓  逆向容器格式 + 派生密钥
```

四道关卡的解法互相独立，下面逐条说。

---

## 1. 沙盒：连 root 都读不了的目录

微信的数据在：

```
~/Library/Containers/com.tencent.xinWeChat/Data/Documents/xwechat_files/
```

实测（`sudo ls`、甚至系统级守护进程都试过）：

```
$ ls ~/Library/Containers/com.tencent.xinWeChat/Data/Documents/xwechat_files
ls: Operation not permitted
```

这不是普通权限位的问题，是 **TCC（Transparency, Consent, and Control）**：
即使是 root，没有用户的明确授权也读不了 App 容器。给终端开「完全磁盘访问」
能解决一部分，但微信容器在部分 macOS 版本上仍然拒绝。

**绕过思路**：不需要自己读——让微信帮我们读。

微信进程自己当然能访问自己的容器，而且它的 entitlements 里带着：

```
com.apple.security.app-sandbox
com.apple.security.files.downloads.read-write      ← 关键
```

也就是说，**微信进程可以往 `~/Downloads` 里写文件**。于是：

1. 用 lldb 附加到微信进程；
2. 在它里面求值一段 C 代码，调用 `clonefile(2)`；
3. `clonefile` 是 APFS 的写时复制，把容器里的目录「克隆」到 `~/Downloads`，
   **瞬间完成，且不占额外空间**（同一份数据两个名字，直到有一方被改写）。

```c
extern "C" int clonefile(const char *, const char *, unsigned int);
(int)clonefile(("…/xwechat_files/wxid_xxx/db_storage"), ("~/Downloads/wx_dump/db_storage"), 0)
```

拿到这份副本之后，所有后续操作都是**离线**的：微信关掉也照样能分析。

> 顺带一个副产品：`wxwalk` 命令也是同样的套路——在微信进程里跑一个
> `opendir/readdir` 递归，把目录清单写到 `~/Downloads`，用来确认容器里都有什么。

## 2. 签名：Hardened Runtime 拒绝调试器

第一反应是直接 `sudo lldb -p <微信pid>`，结果：

```
error: Not allowed to attach to process.  Reason: Not allowed to attach to process.
```

原因是腾讯官方签名开启了 **Hardened Runtime**（`codesign -dvvv` 里能看到
`flags=0x10000(runtime)`）。这个开关会让内核拒绝任何调试器附加，
**root 也不行**——除非进程自己带 `com.apple.security.get-task-allow`，
而官方签名显然不会带。

**绕过思路**：不动原版，复制一份，只改副本的签名。

```bash
ditto /Applications/WeChat.app ~/wechat-extract/WeChatRun.app
# 去掉 Hardened Runtime，但保留每个组件原有的 entitlements
codesign --force --sign - --entitlements <原entitlements> --timestamp=none <每个Mach-O和bundle>
```

重签名有两个坑，脚本 `bin/_sign_app.sh` 里都处理了：

1. **必须保留 entitlements**。WeChat 是沙盒 App，一旦丢掉
   `com.apple.security.app-sandbox`，它就访问不了自己的容器，前功尽弃。
2. **必须由内向外签**。bundle 里的 nested code（frameworks / appex / xpc /
   dylib）要先签，外层 bundle 后签，否则外层签名seal不上内层。

代价：副本签名和官方不一致，微信不认这台设备的登录凭据，**需要重新扫码登录一次**。
原版 App 自始至终一个字节都没改过。

> 有意思的是，微信有自愈机制：过一段时间它会主动把被改过的 bundle 换回官方构建。
> 所以这个「可调试窗口」是临时的，抓完密钥就没了——但**密钥是一次性成本**，
> 存下来之后再也不需要走这条路。

## 3. SQLCipher：让微信自己把密钥说出来

### 3.1 密钥是怎么派生的

微信 4.x 用的是 SQLCipher。挂上断点后可以看到它对每个库都调用：

```c
CCKeyDerivationPBKDF(
    kCCPBKDF2,
    password,        32,       // ← 账号级随机口令，整个账号共用一个
    salt,            16,       // ← 目标数据库文件的前 16 个字节
    kCCPRFHmacAlgSHA512,
    256000,                    // ← 迭代轮数
    derivedKey,      32);      // ← 结果直接当 AES-256 key 用
```

关键点：**派生出的 32 字节不再做任何变换，直接就是 SQLCipher 的 raw key**。
所以只要拿到那个 32 字节的 `password`，配合每个库自己的文件头 salt，
就能离线算出所有库的密钥：

```python
key = pbkdf2_hmac("sha512", passphrase, db_file[:16], 256000, 32)
conn.execute('PRAGMA key = "x\'%s\'"' % key.hex())
conn.execute("PRAGMA cipher_page_size = 4096")
```

### 3.2 抓口令

`password` 是随机数，磁盘上算不出来，只能在微信做 PBKDF 的那一刻读它的入参。
lldb 的 Python 脚本断点可以做到（`lldb/wxcap.py`）：

```python
b = target.BreakpointCreateByName("CCKeyDerivationPBKDF")
b.SetScriptCallbackFunction("wxcap._pbkdf_cb")
```

回调里按 ARM64 调用约定取寄存器：`x1/x2` 是 password 指针/长度，
`x3/x4` 是 salt 指针/长度，`x6` 是轮数。看到 `rounds == 256000` 的那条，
`password` 就是账号口令。

同时还会断 `CCCryptorCreate`，直接抓 32 字节的 AES key，用来交叉验证。

> **注意别抓错**：派生过程中还有 `rounds == 2` 的调用（那是单库派生密钥，
> password 字段其实是别的东西）。只有 256000 轮的那条才是账号口令。
> 更严格的校验是拿候选口令去解 2 个以上的库，都能打开才算数。

抓到的记录落在 `keys/capture.jsonl`：

```json
{"t":"pbkdf","rounds":256000,"pwlen":32,"saltlen":16,
 "pw":"2cc75d…84ff","salt":"4cf675…8124"}
```

### 3.3 打开之后

`sqlcipher3` 连上以后，`sqlite_master` 里能看到表。几个关键库：

| 库 | 内容 |
|---|---|
| `session/session.db` | 会话列表（`SessionTable`：508 条） |
| `contact/contact.db` | 联系人、群、群成员 |
| `message/message_0.db` | 近期消息，每个会话一张 `Msg_<md5(会话id)>` 表 |
| `message/message_1.db` | **更早的历史分片**（同一个会话可能有同名表，两段拼起来才是全量） |
| `message/biz_message_0.db` | 公众号/服务号消息 |
| `hardlink/hardlink.db` | 图片/文件/视频的 md5 ↔ 本地文件名索引 |
| `emoticon/emoticon.db` | 表情包元数据 |

> 特别提醒：`Msg_<md5>` 这个名字是 `md5(会话ID)`。所以想反查某个表属于谁，
> 要把 session/contact 里所有用户名都拿来做一次 md5，建反查表。

## 4. 消息正文：两层包装

`message_content` 不是直接可读的：

1. **压缩**：`WCDB_CT_message_content == 4` 表示正文是 zstd 压缩的（群聊大消息基本都压缩）；
2. **发送者前缀**：群聊正文最前面是 `<发送者wxid>:\n`。

解开之后大多是一段 XML，按 `local_type`（取低 32 位，高位是标志）区分：

| local_type | 含义 |
|---|---|
| 1 | 文字 |
| 3 | 图片 |
| 34 | 语音 |
| 42 | 名片 |
| 43 | 视频 |
| 47 | 表情包 |
| 48 | 位置 |
| 49 | 应用消息（子类型 57=引用、6=文件、5=链接、2000/2001=转账/红包、19=合并转发…） |
| 50 | 语音/视频通话 |
| 10000 | 系统消息（`<sysmsg>`，含「谁邀请谁入群」这类模板） |

## 5. 图片：`.dat` 的容器格式

### 5.1 V2 容器

本地缓存的图片长这样：

```
偏移  长度  含义
0     6     magic  07 08 56 32 08 07          ("\x07\x08V2\x08\x07")
6     4     aes_size   ← 前这么多字节是 AES 加密的
10    4     xor_size   ← 末尾这么多字节是与单字节异或的
14    1     保留
15    …     payload
```

解：

```python
pt_aes = AES_ECB_decrypt(key, payload[:align16(aes_size)])[:aes_size]
pt_raw = payload[align16(aes_size) : len(payload)-xor_size]
pt_xor = bytes(b ^ xorkey for b in payload[len(payload)-xor_size:])
plain  = pt_aes + pt_raw + pt_xor
```

* **AES key**：`md5(uin + wxid)[:16]`。`wxid` 是账号，`uin` 在
  `ilink/*/kvcomm/config.ini` 的 `last_uin`（base64）里。
* **异或字节**：不写死。JPEG 明文结尾固定是 `FF D9`，所以把一批文件的最后一个
  字节和 `0xD9` 异或，取众数就是 key（实测是 `0x70`）。
* **老格式 V1**：magic 不同，AES key 是固定串 `cfcd208495d565ef`。
* **纯异或**：少数文件没有 magic，用已知图片文件头反推单字节 key。

### 5.2 怎么把文件对上消息

消息 XML 里的 `md5` 属性就是**解密后明文的 md5**：

```python
assert md5(plaintext) == message_xml_md5     # 实测 100% 成立
```

所以做法是：把某个会话媒体目录里所有 `.dat` 都解一遍，算明文的 md5 建索引，
再用消息里的 md5 去查。`_t.dat` 是缩略图，只在原图没缓存时兜底。

### 5.3 wxgf / HEVC

新版微信有些图片解密出来开头是 `wxgf`，里面塞的不是 JPEG 而是 **HEVC 码流**。
用 PyAV 解成普通 JPEG：

```python
container = av.open(BytesIO(data[i:]), format="hevc")
frame.to_image().save(buf, format="JPEG", quality=92)
```

### 5.4 覆盖率的真相

**微信只缓存你点开过的图片。** 所以「消息里有 N 条图片，只导出 M 张」是正常的。
没缓存的消息会保留 `[图片]（本机无缓存 md5=…）` 的标记，而不是凭空变出来。
想提高覆盖率只有一个办法：在微信里把那些图片点开一次，然后重新跑一遍导出。

## 6. 表情包：微信压根不存

收到的表情微信**不落盘**——它只在消息 XML 里给一个带签名的 CDN 地址：

```xml
<emoji md5="…" cdnurl="http://…/…" …/>
```

所以只能顺着链接去取。链接有有效期，越早取回得越多。取回来的文件按 md5 命名，
放在 `export/共享资源/表情包/`，所有会话共用一份，靠相对路径引用，不重复占空间。

## 7. 为什么不用现成的开源工具

2026 年这一波工具基本都被下架了：

* `sjzar/chatlog` —— 仓库已被作者清空（收到微信官方函件）；
* `0xlane/wechat-dump-rs`、`ylytdeng/wechat-decrypt` 等 —— GitHub 以 DMCA 屏蔽（HTTP 451）；
* `LC044/WeChatMsg` —— 只支持 Windows，不支持 macOS；
* `wechat-cli` 之类 —— 解析逻辑绑死旧版本（如 4.1.8），新版直接用不了。

而这套方法**不依赖任何版本相关的偏移**：密钥靠断点抓、容器格式靠逆向，
所以只要微信还在用 SQLCipher + 同一套 PBKDF 调用，换版本也能用。

---

## 8. 安全与边界

* 全程**只读**：所有数据库都以 `PRAGMA query_only = ON` 打开；
  沙盒数据是写时复制的副本，原版 App 从未被修改。
* 只有在**抓密钥**这一步会重启微信、需要重新登录一次；之后全部离线。
* 产物（`keys/`、`export/`、`data/`）都是私密数据，不要外传或上传。
* 这套东西的用途是导出**你自己账号**在你**自己设备**上的数据。
