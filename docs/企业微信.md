# 企业微信（WeCom / WXWork 5.x）本地记录导出

## 2026-10 增量与媒体约定

增量默认按账号／数据集／会话／源表／消息 ID 记录已输出身份，识别同秒、迟到和已编辑消息。旧时间水位迁移会将当前可用消息重放一次，避免猜测遗漏范围。显式 `--since` 查询不会更新日常进度。

TXT/CSV/HTML 和 `_messages.json` 一起生成；合并按 ID 更新，不用正文前 200 字去重。旧 CSV 只有在对应快照能唯一匹配每一行时迁移；无法匹配或同内容多 ID 时停止，保留旧文件。

媒体按账号隔离。数据库账号和 Profiles 档案 ID 可能不同；在同一完整原始快照中只有一个账号和一个档案时可唯一绑定。多账号不明确时使用原始快照中的 `_profile_accounts.json`，映射数据库账号 ID 到档案目录名。

`wecom_export.py` 支持 `--raw`、`--plain`、`--out`、`--no-media`；`wecom_recent.py` 还支持 `--key`、`--watermark` 和 `--merge`。默认自检不读取本人数据，真实快照兼容性检查须显式传 `--real-snapshot`。

Node inspector 的既定读取路径及 wxSQLite3 AES 分页格式保持不变。明文 SQLite 也合并已提交 WAL；快照或解密失败不会替换上一份有效数据。

---

跟个人微信那套**完全独立**：容器、账号体系、加密算法、表结构都不一样，代码也不共用。
用户看 [`../使用说明.md`](../使用说明.md)；这里写给维护者。

## 1. 三步命令

```bash
./.venv/bin/python scripts/wecom_snapshot.py        # ① 拉快照（不动企业微信）
./.venv/bin/python scripts/wecom_snapshot.py --with-media   # ①' 连聊天附件一起（明文，COW，大小取决于附件缓存）
./.venv/bin/python scripts/wecom_capture_key.py --sign-only # ②' 只复制+重签副本（不用退出企业微信）
./.venv/bin/python scripts/wecom_capture_key.py --yes --wait 600   # ② 抓密钥（要先退出企业微信）
./.venv/bin/python lib/wecom/extract.py             # ③ 解密
./.venv/bin/python scripts/wecom_inspect.py         #    认真实表结构
./.venv/bin/python scripts/wecom_export.py          #    导出（会话快照 + 附件 + 有 key 时的消息）
./.venv/bin/python scripts/wecom_export.py --no-media       # 不搬附件
./.venv/bin/python scripts/wecom_selftest.py        #    自检（造假的加密库跑全流程）

# —— 日常只用这一条：只捞新产生的聊天记录（无感）——
./.venv/bin/python scripts/wecom_recent.py           # 上次之后的新消息
./.venv/bin/python scripts/wecom_recent.py --since 2h
./.venv/bin/python scripts/wecom_recent.py --chat 产品群 --merge   # 顺带并进主导出
```

对应 `bin/7-企微-拉快照.command`、`bin/8-企微-抓密钥.command`、`bin/9-企微-导出.command`，
以及日常用的 **`bin/10-新消息.command`**。

### 命令行速查（含微信）

```bash
./bin/10-新消息.command                      # 两个 App 一起：只看新消息
./.venv/bin/python scripts/wecom_recent.py --since 2h --merge
./.venv/bin/python scripts/wx_recent.py      # 微信：刷快照 + 只重导有变化的会话
```

### 增量导出（无感）

`scripts/wecom_recent.py` 做的事：借企业微信自己的 Node 子进程（`SIGUSR1` → inspector
→ 沙盒 shell）把**只有数据库的那份**快照 clonefile 出来（几十 MB、秒级，不搬附件缓存），
解密后按水位线 `data/wecom/.watermark.json` 筛出新消息，写到
`export/wecom/增量/<时间戳>/`，终端同时打印摘要。

* 不 attach 调试器、不注入、不改 App、**不重启**、不弹系统授权框、**不抢焦点**；
* 密钥早就有，不需要再动企业微信一次；
* `--merge` 会把新消息按内容去重后追加进主导出，让 `export/wecom/index.html` 一直是最新的。

### 已经验证到哪一步

`scripts/wecom_selftest.py` 会造一份**格式一致、内容为假**的数据集（真 SQLite →
`crypto.encrypt_page` 逐页加密 → 造一段已提交的 WAL），然后把
「候选密钥扫描 → 解密整库 → WAL 合并 → 解析消息/成员 → 渲染导出 → 真实
`conv_snapshot` 解析 → protobuf 解码」整条链跑一遍，**23 项全过**。

`wxsalt` 抓 key 也做过端到端自检：用一个自己写的假目标（调用
`CC_MD5(raw||page||"sAlT")`）验证 lldb 挂钩确实能取回那 16 字节。

所以唯一还没验证的，就是「重签副本能不能起来并解密真库」——那需要退出一次企业微信。
副本本身已经试过 `--sign-only`：`flags=0x2(adhoc)`（Hardened Runtime 已去掉），
`app-sandbox` / `application-groups` / `downloads.read-write` 三个 entitlements 都保住了，
`codesign --verify --deep --strict` 通过。

## 2. 为什么读它的数据这么费劲

| 障碍 | 实测结论 |
|---|---|
| 容器 TCC | `~/Library/Containers/com.tencent.WeWorkMac/Data` 外部进程（**含 root**）读是 EPERM。日志原文：`System Policy: deny(1) file-read-data …/Data`，服务是 `kTCCServiceSystemPolicyAppDataDetailed`。软链接、`/System/Volumes/Data`、`..` 绕路全部无效（TCC 是 vnode 级的）。 |
| `lldb` | 官方签名 `flags=0x10000(runtime)`（Hardened Runtime）且**没有** `get-task-allow`，附加被拒。 |
| `task_for_pid` | 内核拒绝，root 也一样：`macOSTaskPolicy: … is hardened, … doesn't have get-task-allow, … is not a declared debugger`。 |
| `dtrace` | SIP 开启，`dtrace -p <pid>` → `failed to grab pid`。 |
| `leaks` / `heap` | macOS 27 给 Apple 自家工具发了只读 task port entitlement，`vmmap`/`leaks`/`heap` 能跑，但**只能 show/save readonly memory 的内容**，可写堆里的 key 拿不到（用过 canary 验证）。 |
| 私有 entitlement | 给测试程序加 `com.apple.private.tcc.allow` 直接被 AMFI `Killed: 9`。 |
| 磁盘上有没有 key | 没有。key 由服务端在登录时下发（`GidLoginServiceImpl::GetAllLocalEncryptKey` / `QueryUserDBKeys` → `CRTX.GetPcLocalEncryptKey*`，见二进制符号）。`Config.bin` 是 `local_encrypt` 子系统的密文，而那个子系统的 key 也来自服务端 —— 鸡生蛋。 |

### 那怎么读到的？—— Node inspector 借沙盒

企业微信会拉起两个 **Node.js 子进程**：

```
.../Resources/WeDrive/v14.17.4/bin/node .../WeDrive/res/node.js
.../Resources/wemail_resource/wemail_node/main.js
```

它们是主进程的孩子，**继承了企业微信的沙盒与容器授权**。Node 有个官方开发特性：
给进程发 `SIGUSR1` 就在 `127.0.0.1:9229` 起一个 inspector。于是：

```
SIGUSR1 → CDP Runtime.evaluate → child_process.execFile('/bin/sh')
```

我们就得到**一个跑在企业微信沙盒里的 shell**。写入位置限于它有权的目录（`~/Downloads`），
所以在那里 clonefile 克隆一份，再原地 `mv` 进项目。

实现：`lib/wecom/access.py`（沙盒通道）、`lib/wecom/cdp.py`（手写的极简 CDP 客户端，
只用标准库）。**不 attach、不注入、不改 App、不重启、不弹系统授权框。**

## 3. 加密格式（wxSQLite3 风格 AES-128-CBC）

* 页大小 4096，**没有**个人微信 SQLCipher 那 80 字节 reserve/HMAC 区；
* 每页 AES key = `MD5(raw_key(16) || LE32(page_no) || b"sAlT")`；
* 每页 IV 由页码驱动的一串线性同余伪随机数再取 MD5；
* 第 1 页保留 SQLite header 碎片：`page[16:24]` 存明文 `10 00 02 02 00 40 20 20`，
  密文流是 `page[8:16] || page[24:]`，解出来前面 8 字节要和 `page[16:24]` 对上；
* 校验 key：解第 1 页后以 `SQLite format 3\0` 开头，且第 100 字节 ∈ {2,5,10,13}。

实现：`lib/wecom/crypto.py`（含 WAL 合并；`encrypt_page` 只给自检用）。

**key 是每台机器一份的随机 16 字节**，不写在任何配置文件里。

## 4. 抓 key：必须动一次企业微信，而且**必须用内存转储**

`bin/_sign_app.sh` 会把 App 复制一份并**逐组件**重签名（保留各自的 entitlements，
所以沙盒与容器权限都还在），同时**丢掉 Hardened Runtime**。副本起来以后 `lldb` 就能附加。
实测副本：`flags=0x2(adhoc)`，`app-sandbox` / `application-groups` / `downloads.read-write`
都在，`codesign --verify --deep --strict` 通过；而且**不用重新扫码**——它直接续上了登录态
（起来就能打开 message.db / session.db / user.db）。

### 不要指望断点（这条是踩出来的）

一开始我照个人微信那套，把断点下在 `CC_MD5` / `CC_MD5_Update` 上，**一条都没抓到**。
企业微信的 wxSQLite3 页密钥派生用的是**静态链接的 OpenSSL MD5**
（二进制里有 `md5_block_data_order` / `MD5_Init` / `MD5_Update` / `MD5_Final`），
根本不走 CommonCrypto。改宽到 `MD5_Update` 之后仍然抓不到 —— 因为还要赌
「某一刻刚好在解页」，而副本起来后基本是空闲的（CPU 0.3%）。

### 可靠做法（`scripts/wecom_capture_key.py` 现在就是这么做的）

```
lldb attach → wxdump 把副本所有「可写且不可执行」的内存段导出（大小取决于进程内存，通常 GB 级）
            ↓
native/wecom_keyscan.c（C + OpenSSL，8 线程）逐 16 字节窗口验证：
    MD5(cand ‖ LE32(1) ‖ "sAlT") → AES-128-CBC 解第 1 页密文流首块 → 比对 header 碎片
            ↓
命中 → 用真实库第 1 页复核 → 写 keys/wecom_key.json(0600) → **立刻删掉内存镜像**
```

扫描速度取决于内存大小与机器；候选命中后必须用真实库第 1 页复核并去重：

```
raw key = b404495e0106b6d544f33b8d481b8c7c      ← 一把钥匙开 16 个库
```

> 内存镜像含明文 key，是敏感数据：脚本扫完立刻 `rm -rf .runtime/memdump`，
> 不要留着、更不要外传。

## 5. 数据布局（本机实测）

```
~/Library/Containers/com.tencent.WeWorkMac/Data/
├── Library/Application Support/WXWork/Data/
│   ├── <corp-id>/                    ← 账号（corp uid）
│   │   ├── Data/{message,session,user,file,kv,company,crm,…}.db   加密
│   │   ├── Index/{data_index,message_index_log,…}.db              部分明文
│   │   ├── Backup/<ts>/Data/…                                    加密备份
│   │   ├── Config.bin (2784B)                                    local_encrypt 密文
│   │   ├── Emotion/ Avator/ Cache/…
│   │   └── …
│   └── Global/{Config.bin (17328B), Image/, Statistic/…}
├── Documents/
│   ├── Profiles/<32hex>/conv_snapshot      ← **明文 protobuf**：会话列表 + 最后一条消息
│   ├── Profiles/<32hex>/Messages1/*.db     ← CEF 侧消息/搜索库（加密）
```

## 6. 明文快照 `conv_snapshot`（不需要密钥）

CEF 侧会把「会话列表 + 每个会话最后一条消息」以**明文 protobuf** 落盘。
文件布局 `[u32 长度][32 字节 hex][u32 载荷长度][protobuf]`，顶层是一串 field 1：

| 字段 | 含义 |
|---|---|
| 1 | 会话 id (int64) |
| 2 | 会话对象 id |
| 3 | 会话显示名 |
| 6 | 最后消息时间 (unix) |
| 10 | 最后一条消息：1=消息id，4=发送者id，8=发送时间，**10.1.2.1=正文**，14=内容类型，15.4=发送者显示名 |

解析器：`lib/wecom/conv.py`；通用 protobuf wire 解码器：`lib/wecom/pbwire.py`
（消息体里大量结构都是 protobuf，后面解析 `message.db` 也用得上）。

## 7. schema 与覆盖率（版本相关，别照抄）

### schema（5.x，`PRAGMA table_info` 实测）

* `message.db` → **`message_table`**（17 列）：
  `message_id, server_id, sequence, sender_id, conversation_id, content_type,
  send_time, flag, content, devinfo, from_app_id, msg_from_devinfo,
  extra_content, local_extra_content, client_id, …`
  另有 `message_appinfo`、`kf_message_tableV1` / `message_small_table`（行数取决于账号）。
* `session.db` → **`conversation_table`**（`id, name, last_message_time, …`）；
  `conversation_user_table` / `conversation_member_nickname_table` 可能为空
  → 群昵称拿不到时只能退回通讯录名字。
* `user.db` → `user_table`（本公司同事）、`wechat_contactV1`（微信联系人）、
  `external_user_relation_v3`（外部联系人备注）、`room_robot`、`department_tableV2`。
  显示名要把这几张表**合起来**查。
* 会话 id 前缀：`R:` 群、`S:` 单聊、`M:` 微信联系人、`Y:`/`O:` 系统或应用。
  `S:` 的 id 形如 `S:<对方id>_<本人id>`，取名字时要跳过本人那一段。

### `content` 的三种形态（实测）

| 形态 | 例子 | 处理 |
|---|---|---|
| 明文 UTF-8 | `企业微信团队创建` | 直接用 |
| XML | `<msg><appmsg><title>周报.docx</title>` | 剥出 `title`/`des`；**绝不把原始 XML 摊进记录** |
| protobuf | `\n<正文`、`\n\xda\x01<十六进制>` | 先按 protobuf 解；解出来若是十六进制再解一层；实在解不动就捞最长可读串 |

`content_type` 常见值：0/2/123 文本类、13 文档链接、29 文件、31 链接、503 图片、
573 文件 md5、14/15 十六进制外壳（解出来是 UUID / 消息 id）。

### 覆盖率（**别宣称"全部导出了"**）

| 内容 | 来源 | 结果 |
|---|---|---|
| 全部聊天消息 | `message.db`（加密） | ✅ 全量读取，0 缺失 |
| 会话 | `session.db`（加密） | ✅ 与消息实际出现的会话对齐 |
| 通讯录 / 成员 | `user.db`（加密） | ✅ 合并同事与微信联系人 |
| 会话列表 + 最后一条消息 | `conv_snapshot`（明文，不需要 key） | ✅ 取决于 CEF 侧快照 |
| 聊天附件 / 图片 / 视频 / 语音 / 表情 | `Profiles/<id>/Caches/`（**明文**） | ✅ 本机缓存中有多少就带出多少 |
| 群昵称 | `conversation_user_table` | ⚠️ 该表可能为空 |
| 收藏 / 朋友圈 / 邮件 / 微盘 / 会议 | 各自的库 | ❌ 不在本次范围 |
| 语音转文字 | `msg_voice2text` | ❌ 通常为空；语音本身是 SILK，可用可选 ASR 模块离线转写 |

导出不变量（`scripts/wecom_selftest.py` 会跑前三条的同类断言）：

1. 每个会话目录都有 `聊天记录.txt` / `聊天记录.csv`，且 CSV 有 `发送者` 列、不为空；
2. **CSV 条数合计 == `message_table` 行数**；
3. 同名会话不会互相覆盖（`系统/应用` 里有一堆同名条目，必须加唯一后缀）；
4. 原始 XML / 二进制不会摊进正文。

## 8. 边界与隐私

* 原版 `/Applications/企业微信.app` **一个字节都不动**；重签的只是 `.runtime/WeComSigned.app`；
* 只读企业微信自己的容器，不写回、不发消息、不点 UI；
* inspector 会一直开着直到那个子进程重启。收工可以关：
  `python -c "import sys;sys.path.insert(0,'lib');from wecom import access;print(access.close_inspector(9229))"`
  （企业微信重启也会自动关掉。）
* `data/wecom/`、`export/wecom/`、`keys/wecom_key.json` 都是私密数据，别外发。
* 企业微信的账号与聊天记录在企业侧通常被视作公司资产，导出**本人设备上的本人数据**做备份是边界，
  别拿去做别的。
